# ML

## CV/ML-задачи в системе

- **Детекция лица** — найти bbox и 5 keypoints лица в кадре. Подход: SCRFD (InsightFace); на слабом edge без GPU — MediaPipe/YuNet.
- **Alignment** — привести лицо к канонической позе по keypoints от SCRFD перед подачей в embedding-модель.
- **Оценка качества кадра** — отсечь заведомо непригодные кадры (размытие, плохой ракурс, засветка) до дорогого matching. Подход: для PoC — прокси-метрики (размер лица, blur/Laplacian variance, pose angle, brightness); для целевой архитектуры — CR-FIQA/MagFace.
- **Liveness/anti-spoofing** — отличить живого человека от фото/видео/печати. Подход: Silent-Face-Anti-Spoofing (passive, pruned MobileFaceNet).
- **Извлечение эмбеддинга** — получить 512-D векторное представление лица. Подход: ArcFace, InsightFace buffalo_l (ResNet-50, w600k_r50), cosine similarity над L2-нормализованными векторами.
- **Matching (1:N)** — найти ближайших кандидатов в галерее сотрудников. Подход: FAISS HNSW индекс.

## Verification vs identification

Verification — задача 1:1: «это действительно X?» (пример — разблокировка телефона своим лицом против одного заявленного шаблона). Identification — задача 1:N: «кто это из всей галереи, если вообще кто-то?».

На проходной это **identification (1:N)**: сотрудник не предъявляет заявленный ID, система ищет совпадение по всей галерее кампуса (сотни тысяч лиц). Это меняет метрики: вместо FAR/FRR (verification, 1:1) используются **FPIR/FNIR** (identification, 1:N) — False Positive/Negative Identification Rate, которые растут с размером галереи (больше кандидатов — выше шанс случайного ложного совпадения). Это же диктует требование к ANN-индексу: нужен полноценный sub-second поиск по всей базе, а не сравнение с одним шаблоном.

## One-to-many поиск (ANN)

Выбор — **FAISS HNSW**: высокий recall при латентности в десятые доли мс на 10^5–10^6 векторах, поддерживает инкрементальные вставки без полной перестройки индекса (важно — enrollment новых сотрудников не должен требовать простоя). Плата — память (граф связей поверх векторов).

Альтернатива — **IVF-PQ**: сжимает векторы (product quantization), кратно экономит память на больших галереях, но теряет recall из-за квантования и требует переобучения quantizer при существенном дрейфе распределения эмбеддингов. При росте кампуса до нескольких площадок и миллиона+ лиц IVF-PQ — кандидат на upgrade, если память станет bottleneck; на текущем масштабе (сотни тысяч) HNSW предпочтительнее по recall.

Локальная реплика индекса обязательна на edge (см. `docs/architecture.md`, «Edge vs central»): sub-second 1:N поиск по сети до центрального индекса на каждый проход не укладывается в p95 ≤ 1с и не переживёт обрыв связи с центром.

## Пороги и three-way decision

Policy engine принимает решение по совокупности скоров, не по одному порогу:

- `match_score ≥ T_high` **и** `margin_to_second_best ≥ M` **и** `quality.quality_score` выше порога **и** `quality.liveness_score` выше порога → `decision=allow`.
- `match_score < T_low` → `decision=deny`.
- Всё остальное (малый margin, низкое качество, сомнительный liveness, `degraded_mode=true`) → `decision=manual_review`, `requires_human_review=true`.

Обоснование консервативного `T_high`: цена ошибок несимметрична — false accept (пропуск постороннего) это инцидент безопасности, false reject — только рост очереди и раздражение сотрудника. Поэтому порог сдвинут в сторону меньшего FPIR ценой более высокого FNIR, а не выбирается по балансу accuracy.

Калибровка — по методологии NIST FRVT-стиля: **FAR/FRR** для 1:1-компонентов, **FPIR/FNIR** для итогового 1:N-решения (т.к. FPIR растёт с размером галереи). Стартовый ориентир — cosine threshold 0.30–0.45 при целевом FMR≈1e-5, но порог не константа между версиями модели/популяций — пересчитывается на своих данных при каждом обновлении модели или заметном сдвиге состава сотрудников. Обязательна проверка порогов не только в среднем, но и по демографическим подгруппам (пол, возраст, оснащение камеры/освещение по проходным) — по данным NIST FRVT false-positive-дифференциалы между подгруппами могут различаться на порядки сильнее, чем false-negative. Для MVP это не blocker, но обязательный пункт production-чек-листа.

## Что правилами, а что моделью

Модели вычисляют **скоры**: detection confidence, `quality.quality_score`, `quality.liveness_score`, `match_score`, `margin_to_second_best`. Итоговое **решение** — `decision` (allow/deny/manual_review), `degraded_mode`, `requires_human_review` — детерминированный policy engine поверх этих скоров и настраиваемых порогов, отдельный от inference компонент.

Причины разделения: объяснимость (`reasons[]` формируется из явных правил, а не из скрытого состояния модели), аудируемость (audit log хранит `threshold_version` отдельно от `model_version` — понятно, что именно изменилось между инцидентами), возможность оперативно менять политику (ужесточить порог после инцидента, включить `degraded_mode` для конкретной проходной) без переобучения или передеплоя моделей.

## Baseline и метрики выбора

**Baseline**: SCRFD-500M/2.5G (лёгкая версия детектора) + buffalo_l (ArcFace) + FAISS Flat (полный перебор, без ANN-аппроксимации) — самый простой вариант для валидации пайплайна на малой галерее. Апгрейд до FAISS HNSW обязателен при росте базы до десятков тысяч+ лиц, когда Flat перестаёт укладываться в sub-second.

**Метрики сравнения кандидатов моделей**:
- Detection/embedding: FAR/FRR, EER, ROC/PR-кривые на verification-сплите; FPIR/FNIR на identification-сплите (полная галерея).
- Liveness: APCER (доля пропущенных атак), BPCER (доля отклонённых живых), ACER = среднее (ISO/IEC 30107-3); порог калибруется на фиксированном BPCER (например BPCER@1%).
- Latency per stage — таблица ниже, ключевой аргумент для p95 ≤ 1с.

| Стадия | Модель/компонент | Ориентир GPU-латентности |
|---|---|---|
| Detect | SCRFD | единицы мс |
| Quality | FIQA-прокси | <1 мс |
| Liveness | Silent-Face (MobileFaceNet) | единицы мс |
| Embed | ArcFace buffalo_l, 512-D | единицы мс |
| 1:N search | FAISS HNSW (10^5–10^6 векторов) | <1 мс |
| **Итого inference** | | **~15–20 мс**, остальное до 1с — сеть/захват кадра/актуация турникета |

Риск: любая стадия на CPU вместо GPU ломает бюджет на порядок — это прямое обоснование GPU на edge-узле.

## Validation set и delayed labels

Validation-выборка собирается со **сплитом по личностям, а не по кадрам**: один и тот же человек не должен встречаться и в train, и в test — иначе data leakage завышает метрики. Выборка должна покрывать разные камеры, дни, условия освещения, occlusion (маски, очки, головные уборы), и отдельно проверяться по демографическим подгруппам (см. «Пороги и three-way decision»).

**Delayed labels** — источники ground truth, поступающие с задержкой после решения системы: ручные вердикты охраны по `manual_review`-случаям, жалобы сотрудников на необоснованный `deny`, повторный проход по резервному способу (карта) сразу после отказа модели. Эти события используются офлайн для пересчёта FRR/FNIR на реальном трафике (а не только на статичном validation-сете) и периодического пересмотра порогов.

## LLM в системе — где да, где нет

LLM **не используется в hot path** принятия решения allow/deny: недетерминированность вывода, отсутствие калиброванных вероятностей (несовместимо с методологией FAR/FRR/FPIR/FNIR), дополнительная латентность и расширение attack surface (prompt injection через метаданные события) — неприемлемо для биометрического security-решения, где сбой означает либо инцидент безопасности, либо необоснованную блокировку сотрудника.

Вне hot path, в read-only режиме, LLM уместен: человекочитаемое объяснение причин `manual_review` для охраны (перевод `reasons[]` и скоров в понятный текст), natural language поиск по audit log, генерация отчётов для security-команды. Во всех этих сценариях LLM не имеет права инициировать `turnstile_command=open` и не участвует в вычислении `decision`.
