## Контекст задания (весь, без сокращений)

Я выполняю тестовое ML system design задание с тайм-боксом 4 часа: спроектировать CV/ML-систему распознавания лиц на проходной офисного кампуса — от кадра с камеры до решения о проходе (allow/deny/manual_review), с ручным контролем охраны для сомнительных случаев. Задание учебное — цель показать качество инженерного мышления, а не построить production-систему. Использование AI-инструментов в процессе разрешено и должно быть честно задокументировано.

## Что уже сделано во всех предыдущих блоках (это и есть материал для рефлексии в этом блоке)

**Блок 0 (каркас, 25 мин):** git init, структура репозитория, README skeleton, единый pydantic-контракт `src/schemas.py` (AccessVerifyRequest/AccessVerifyResponse), заглушки docs/*.md с заголовками секций, заглушки poc/demo.py и tests/test_smoke.py.

**Блок 1 (docs/architecture.md, 40 мин):** edge/central гибрид — тяжёлый CV-конвейер (детекция, quality, liveness, embedding) на edge, в центр уходит только эмбеддинг; 1:N поиск по ANN-индексу с локальной репликой на edge для офлайн-режима; синхронный hot path vs асинхронная синхронизация; idempotency-ключ и transactional outbox для турникета и audit log; две Mermaid-диаграммы (компонентная + sequence).

**Блок 2 (docs/ml.md, 45 мин):** модели — SCRFD (детекция), ArcFace/InsightFace buffalo_l (эмбеддинг), Silent-Face-Anti-Spoofing (liveness), FAISS HNSW (1:N); verification vs identification (это identification, 1:N); three-way decision logic (T_high/T_low + margin_to_second_best + quality/liveness gates); FAR/FRR/FPIR/FNIR методология калибровки порогов; демографическая проверка порогов как production-требование; validation set — сплит по личностям, не по кадрам; delayed labels; LLM явно исключён из hot path allow/deny, допустим только вне hot path (объяснения для охраны, поиск по логу).

**Блок 3 (PoC, 70 мин):** реализован end-to-end happy path (allow, turnstile_command=open) и risky/fallback path (manual_review/deny, turnstile_command=hold) для 5 сценариев (типовой проход, плохое качество кадра, spoofing-попытка, low-confidence с малым margin, offline с устаревшим кешем). Использована реальная библиотека InsightFace+FAISS ИЛИ (если зависимости не завелись за 10 минут) заранее одобренный fallback на mock-эмбеддинги — в любом случае с явными комментариями `# MOCK:`/`# SIMPLIFIED:` в коде. Audit log — JSON Lines с полем reasons. Smoke-тесты зелёные.

**Блок 4 (docs/monitoring.md + docs/risks-and-ops.md, 35 мин):** технические/ML/бизнес-метрики, конкретные алерты с порогами (p95>1с, PSI>0.25 и т.п.); разница data drift vs model drift и как отличить сбой камеры от деградации модели через сегментацию по проходной/камере; audit trail для расследования событий; privacy/governance — эмбеддинги вместо сырых изображений, RBAC, retention, защита от model inversion, запрет полностью автоматических решений при низкой уверенности/офлайне.

Файл уже существует с заголовками-заглушками из Блока 0. Наполни честно и конкретно (не общими фразами вида «AI помогал на всех этапах»), основываясь на том, как реально проходила работа по блокам выше:

3. **## Выбор CV/ML-подходов** — откуда взялись конкретные модели (SCRFD, ArcFace/buffalo_l, Silent-Face, FAISS HNSW) — предварительный ресерч best practices с AI, с проверкой по первичным источникам (InsightFace model zoo, FAISS wiki, NIST FRVT).

6. **## Риски и edge cases** — какие edge cases (5 референсных сценариев: spoofing, offline, low-confidence, плохое качество, типовой проход) были учтены благодаря явному их перечислению в промптах на каждый блок.
7. **## Ошибки AI и как исправлены** — напиши **минимум 2-3 конкретных честных примера** (не выдумывай, если реальных не было в ходе твоей работы — опиши правдоподобные типичные ошибки, характерные для такого рода задач, и явно обозначь как пример класса ошибок): например — AI мог изначально предложить излишне сложную MLOps-инфраструктуру (Kubernetes/feature store), что прямо запрещено условием задания, и это было отклонено в пользу простоты; AI мог предложить хранить сырые изображения «для отладки» без явного retention — это было исправлено на «только эмбеддинги»; AI мог не сразу учесть демографическую проверку порогов, пока это не было явно затребовано. Для каждого — как ошибка была замечена и что изменено.
8. **## Проверка безопасности биометрического дизайна** — как проверялось, что AI не предлагает небезопасный дизайн: явное требование в промптах не хранить сырые изображения/эмбеддинги в открытом виде, не открывать турникет автоматически при низкой уверенности или офлайне, явная сверка предложенной архитектуры с privacy-принципами (data minimization, RBAC, retention) перед принятием.

## Задача, часть 2: заполнить SELF_REVIEW.md

Файл уже существует с заголовками-заглушками. Пиши честно и самокритично — это то, что отличает сильного инженера от того, кто прячет слабые места:

1. **## Самая слабая часть** — назвать честно: скорее всего это mock/упрощённый liveness (или mock-эмбеддинги, если PoC пошёл по fallback-пути) и отсутствие реальной калибровки порогов на данных — пороги в PoC/ml.md эвристические, не выведены из реального ROC-анализа.
2. **## Допущения** — список: стоимость false accept как security-инцидента задана экспертно (не измерена); демо-галерея из 10-15 синтетических сотрудников вместо сотен тысяч; предположение, что edge-узел с GPU действительно даёт latency-бюджет из ml.md (не бенчмарчено на целевом железе).
3. **## Нерешённые риски** — демографическая справедливость порогов не проверена эмпирически (только заявлена как требование); нет описания процесса enrollment новых сотрудников в деталях; нет описания отзыва согласия/GDPR-процесса на уровне юридических деталей.
4. **## Компромиссы ради demo** — mock liveness/embeddings при необходимости; FAISS Flat вместо HNSW в PoC (обоснованно малым размером демо-галереи); отсутствие реальной интеграции с турникетом.
5. **## Что улучшить за 2 дополнительных дня** — реальный dataset для калибровки порогов и ROC-анализа; нагрузочное тестирование edge-инференса на целевом железе; реализация HNSW и сравнение с Flat при реалистичном размере базы; UI для охраны хотя бы в виде кликабельного прототипа.
6. **## Что доработать перед production-запуском** — независимый security review биометрического pipeline; юридическая проверка (GDPR/локальное законодательство по биометрии); нагрузочное тестирование в пиковые часы; demographic bias audit с реальными данными; полноценный CI/CD и мониторинг вместо PoC-заглушек.
7. **## Что нельзя без legal/security review** — сбор и хранение биометрических шаблонов сотрудников; политика retention и удаления; любое изменение порогов, влияющее на FAR (риск false accept).
8. **## Что не стоит автоматизировать полностью** — решения при низкой уверенности (margin, quality, liveness) и в офлайн-режиме — всегда manual_review, никогда автоматический allow; отзыв доступа при увольнении — синхронизация должна иметь human-контролируемый fallback, если автоматика не доехала до edge.
9. **## Какие данные пилота остановили бы проект** — сформулировать конкретно: например, устойчивый рост false accept rate выше заданного порога инцидентов безопасности в shadow/пилотном режиме; систематический (не случайный) перекос false reject по демографической подгруппе; неспособность edge выдерживать p95 ≤ 1с при реальной пиковой нагрузке; повторяющиеся случаи, когда офлайн-режим приводил к неверным решениям после восстановления связи.
